# Sprint 8 Plan — Billing and Commercialization

- Status: Active
- Epic: EP-011 — Billing and Commercialization
- Protected baselines: Sprints 1–7
- Sprint 7 repository/CI baseline: `ddddd495795d3c3b9de84191acb2cf9aa48167e8`

## Objective

Support external paying organizations with tenant-safe plans, subscriptions, billing state, quotas, invoices, licensing, and onboarding while preserving existing product behavior for unpaid/internal tenants and keeping payment-provider side effects explicitly controlled.

## Entry criteria

- Sprint 7 is closed at repository/CI level.
- `make test` and `make test-sprint2` through `make test-sprint7` are protected regression gates.
- Tenant identity, membership authorization, Site Builder, CRM, Customer Portal, Creator Tools, and AI boundaries are established.
- Existing quote/product price metadata is presentation/catalog data only until explicitly linked to Sprint 8 billing records.
- No existing tenant data is reinterpreted as a paid entitlement without an explicit migration rule.

## Locked scope

Sprint 8 covers:

- canonical tenant billing ownership and commercialization threat/boundary audit;
- provider-neutral billing state before Stripe-specific integration;
- explicit subscription plans and tenant plan assignment;
- entitlements/quotas derived from deterministic application records, not payment-provider responses alone;
- Stripe customer/subscription identifiers and webhook reconciliation;
- invoice/payment-history metadata required for tenant administration;
- licensing/feature entitlement checks;
- tenant onboarding/commercialization workflow;
- safe trial/cancel/past-due/suspended states;
- administrative billing visibility and auditability;
- focused Sprint 8 regression and closure evidence.

## Explicit non-scope

- marketplace payouts;
- split payments or connected-account payouts;
- cryptocurrency payments;
- stored card numbers or raw payment credentials;
- arbitrary dynamic pricing generated by AI;
- autonomous refund/credit issuance;
- interpreting legacy `price_text` as canonical charge instructions;
- payment-provider credentials in application tables;
- replacing tenant authorization with payment-provider metadata;
- deleting tenant data solely because billing state changes.

## Safety principles

1. Billing ownership is always one tenant.
2. Provider identifiers are references, not authorization.
3. Entitlements are deterministic and server-side.
4. Webhooks are authenticated, idempotent, and replay-safe.
5. Payment credentials never enter application persistence.
6. Billing failure degrades product capabilities according to explicit policy, never by accidental exceptions.
7. Tenant data remains isolated during billing reads/writes.
8. Cancellation and past-due transitions are reversible where policy allows.
9. Existing internal/non-commercial tenants remain usable unless explicitly migrated.
10. CI never performs real chargeable payment-provider actions.

## Task sequence

### S8-T01 — Billing tenant boundary and commercialization audit

Define canonical tenant ownership, billing data classes, allowed identifiers, and migration rules before provider integration.

Acceptance:
- every billing record belongs to one organization;
- cross-tenant plan/subscription/invoice references fail closed;
- payment credentials/card data are explicitly prohibited;
- legacy catalog/quote price fields are not interpreted as charge authorization;
- internal/non-commercial tenants remain unchanged;
- provider IDs are classified as opaque references only;
- webhook/provider state cannot directly authorize tenant access;
- migration and rollback risks are documented.

### S8-T02 — Plan and entitlement foundation

Add deterministic application-owned plans and entitlements.

Acceptance:
- plans have stable slugs, names, lifecycle, and bounded quota metadata;
- tenant plan assignment is explicit and tenant-scoped;
- feature/quota entitlement checks are server-side;
- unknown entitlements fail closed;
- no Stripe call is required to evaluate current application entitlement.

### S8-T03 — Subscription lifecycle foundation

Add application-owned subscription records and safe lifecycle transitions.

Acceptance:
- explicit trialing/active/past_due/canceled/suspended states;
- subscription belongs to one tenant and one plan;
- transition rules are deterministic;
- cancellation preserves tenant data;
- provider identifiers remain optional opaque references.

### S8-T04 — Stripe integration boundary

Add Stripe adapter/configuration without exposing secrets.

Acceptance:
- Stripe API keys load from environment/secret-manager inputs only;
- application code depends on a narrow billing-provider interface;
- real provider calls are mocked/faked in CI;
- no PAN/card data is persisted;
- provider failures return controlled errors.

### S8-T05 — Stripe customer and checkout onboarding

Create/reconcile Stripe customer and checkout/session references for commercial onboarding.

Acceptance:
- customer/session references are tenant-scoped;
- checkout creation requires authorized owner/admin action;
- return URLs are allow-listed;
- provider response does not itself activate entitlement before reconciliation.

### S8-T06 — Webhook verification and reconciliation

Add authenticated/idempotent Stripe webhook handling.

Acceptance:
- signature verification is mandatory;
- duplicate event IDs are idempotent;
- unsupported events are safely ignored/audited;
- subscription/invoice updates cannot cross tenant boundaries;
- replay/reordering behavior is documented and tested.

### S8-T07 — Invoice and payment-history metadata

Add tenant-visible billing history without storing payment credentials.

Acceptance:
- invoice/payment metadata is tenant-scoped;
- hosted invoice URLs are validated HTTPS references;
- no raw payment method/card details are persisted;
- owner/admin billing reads are bounded.

### S8-T08 — Quotas and commercialization enforcement

Connect deterministic entitlements to selected product limits.

Acceptance:
- quotas are enforced server-side;
- product behavior for exceeded quota is explicit and testable;
- AI usage limits may reference plan defaults but tenant overrides remain controlled;
- billing state cannot bypass existing authorization;
- non-commercial/internal tenants retain explicit policy.

### S8-T09 — Billing administration and onboarding

Add owner/admin commercialization surfaces/helpers.

Acceptance:
- plan/subscription/invoice status can be inspected;
- owners/admins can initiate approved billing lifecycle actions;
- staff/viewers cannot alter billing configuration;
- tenant onboarding is explicit and auditable.

### S8-T10 — Billing operations, recovery, and rollback

Add provider-independent diagnostics and operational procedures.

Acceptance:
- webhook/provider failures are observable without secrets;
- reconciliation can be retried safely;
- kill/maintenance behavior is documented;
- cancellation/past-due recovery procedures are documented.

### S8-T11 — Sprint 8 regression and closure

Add `make test-sprint8`, enforce CI, record rollback evidence, and formally close Sprint 8.

## Testing requirements

- `make test` remains the complete regression gate.
- `make test-sprint2` through `make test-sprint7` remain protected.
- Sprint 8 adds `make test-sprint8`.
- All Stripe/provider calls use fakes/mocks in CI.
- Webhook tests cover signature failure, duplicates, cross-tenant attempts, reordering, and unsupported events.
- Billing/entitlement tests include positive and negative authorization coverage.
- No test requires real money movement.

## Exit criteria

1. Tenant-safe plans/subscriptions/invoices exist.
2. Stripe integration is bounded, secret-safe, and replay-safe.
3. Entitlements/quotas are deterministic and server-side.
4. Commercial onboarding works without reinterpreting legacy tenant data.
5. Existing non-billing product workflows remain compatible.
6. Full protected regression evidence is green.
7. Release/rollback evidence and known limitations are recorded.
